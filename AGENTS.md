# This is NOT the Turborepo you know

Turborepo configuration, task behavior, and CLI commands can vary between installed versions and may differ from your training data. Resolve the `turbo` package from this file's directory or relevant workspace; in monorepos, it may not be visible from the repository root. For example, run `node -p "require.resolve('turbo/package.json')"` from a workspace that depends on `turbo`.

Read `docs/README.md` inside that installed package first, then read the relevant pages from its `docs/` directory before changing Turborepo configuration or commands. Heed deprecation notices. These bundled docs match the installed package version and are available without network access.

This block is written and re-added by `turbo` before repository-scoped commands when an AI agent is detected. In the Turborepo source repository, its template is defined in `crates/turborepo-cli/src/cli/agent_guidance.rs`. Removing the managed block while updates are enabled means a later qualifying invocation will add it again. Set `"agentGuidance": false` in the root `turbo.json` or `turbo.jsonc` to opt out; this does not remove an existing block. Keep the block committed with your work to avoid an uncommitted change on the next agent invocation.

# Working in pkg-guard

Rules for coding agents, and for people. Most are enforced by `pnpm verify`; the rest are here because a review would ask for them anyway. The project is described in [README.md](README.md) and [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md); how to contribute in [CONTRIBUTING.md](CONTRIBUTING.md).

## What the repository is

A pnpm workspace with Turborepo: `apps/backend` (Hono API over SQLite, the job queue, the MCP server), `apps/worker` (the analyzer, runs only in Docker), `apps/frontend` (TanStack Start, server-rendered), `apps/cli` (the command line), `apps/e2e` (Playwright) and `packages/core` (the shared contract, zod/mini). The backend, the worker, the CLI and core are plain Node ESM in TypeScript; the frontend is React 19.

## Before you change anything

- Read the folder you are changing and match the code around it: naming, comment density, how errors are made and how tests are written. Do not introduce a second way of doing something that already has one.
- Ask when a requirement is unclear instead of inventing one. Do not add features, options or abstractions that were not asked for.
- Never edit `apps/frontend/src/routeTree.gen.ts` (generated by the build) or `pnpm-lock.yaml` by hand.

## Code style (enforced by oxlint and oxfmt)

- **Every function is a `const` arrow function**: `export const parseSpec = (value: string): Spec | undefined => { … }`. Never `function parseSpec()`. A generator is the one exception and is written as a function expression (`const chunks = async function* () { … }`).
- **A `const` is not hoisted**: define a function above the code that uses it at module load (a route component above `createFileRoute(...)`).
- **React components take one `props` parameter** typed by a named type declared right above them, and read `props.x`: `type ButtonProps = { … }; export const Button = (props: ButtonProps) => …`. No destructuring in the parameter list and no inline `(props: { … })` type. A component that passes the rest on splits it off inside the body: `const { className, ...rest } = props`.
- **Imports use the package's path aliases, never `../`** and never `./folder/…`. Only a sibling in the same folder may be relative (`./name`). The aliases are every top-level folder of the package plus `@src` and `@tests`:

    | Package         | Aliases                                                                    |
    | --------------- | -------------------------------------------------------------------------- |
    | `apps/backend`  | `@config` `@platform` `@modules` `@composition` `@src` `@tests`            |
    | `apps/worker`   | `@config` `@modules` `@src` `@tests`                                       |
    | `apps/frontend` | `@components` `@config` `@docs` `@lib` `@routes` `@styles` `@src` `@tests` `@vite` |
    | `apps/cli`      | `@src` `@tests`                                                            |
    | `packages/core` | `@src` `@tests` (tests only; `src` keeps relative imports, other packages consume it as source) |

    A new top-level folder gets an alias of the same name in that package's `tsconfig.json` (and, for the backend, in `tests/architecture.test.ts`).

- **Backend, worker, CLI and core imports carry the `.ts` extension**: `import { AppError } from '@platform/errors.ts'`. Frontend imports do not (`moduleResolution: Bundler`).
- **TypeScript strict, and then some**: no `any`, no casts to make the compiler quiet, `type` not `interface`, no unused variables, no empty functions, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are on. Use `undefined`, not `null`, for "no value" unless a contract says otherwise.
- **No `console.log`** (lint allows only `warn` and `error`): the backend and the worker log through pino; `tools/*.js` write to `process.stdout`/`stderr`.
- **`packages/core` runs in the browser and in Node**: no `window`, `document`, `localStorage`, `navigator`, `process` or `Buffer` there, and `zod/mini` instead of `zod`.
- **JSX**: string props in braces (`className={'…'}`), children without (`<p>Text</p>`). Every control has a name; every page one `h1` and a `<main id="main" tabIndex={-1}>`.
- **Formatting is oxfmt's**: 4 spaces, single quotes, trailing commas, `printWidth` 200, one attribute per line in JSX. Run `pnpm format`; never argue with it.

## Architecture rules (enforced by `apps/backend/tests/architecture.test.ts`)

- `platform/` and `config/` know no module; `modules/<name>/` never import another module; only `composition/` wires them together.
- `modules/<name>/application/` has no HTTP and no infrastructure in it: no `hono`, no imports from `http/` or `infrastructure/`.
- The frontend's `src/server.ts` answers documents and share images before the router; every response leaves with the security headers, and an HTML page with its own Content-Security-Policy built from the page's inline scripts.
- Only the worker ever downloads or opens a package, and only in Docker. The API and the frontend never do, and no document for crawlers (`known=1`) may cause a download.

## Comments and language

- **English everywhere**: code, comments, commit messages, documentation, user-facing text.
- **JSDoc on every export** (`/** … */`), one or two sentences saying what it is for; `//` lines inside bodies for the *why*, not the what. Prose sentences with a period, no banners, no `TODO` left behind.
- Do not pad code with comments it does not need; match the density of the file.

## Dependencies

- Exact versions only (`savePrefix: ''`): `"hono": "4.13.12"`, never `^` or `~`. The same in `overrides` in `pnpm-workspace.yaml`.
- A version must be at least 7 days old (`minimumReleaseAge: 10080`); pnpm refuses newer ones. Pick the newest one it allows and say so.
- Add a dependency only when the platform or an existing one cannot do the job; prefer `node:` built-ins. `blockExoticSubdeps` and `strictDepBuilds` are on: nothing from git or a URL, no install script that is not listed in `allowBuilds`.
- `pnpm install` is the only way to change `pnpm-lock.yaml`. Docker base images are pinned by digest, GitHub Actions to a full commit SHA; `pnpm policy` checks all of this.

## Tests

- Unit tests live in each package's `tests/` and run with Vitest (`pnpm test`); browser tests in `apps/e2e` (`pnpm e2e`). A bug fix comes with a test that fails without it; a new route, document or page gets a test in the matching file.
- Tests reach no network: the registry and GitHub are stood in for, the database is in memory, the worker's tests install nothing.
- Never run the worker, `playwright install` or the browser tests on the user's behalf unless asked; they download things.

## Before a pull request

- Run `pnpm verify` (policy, lint, format check, typecheck, tests, build, smoke test) and make it green. CI runs the same, then `pnpm e2e` and the Docker images.
- Update the README, `docs/ARCHITECTURE.md` or `.env.example` when behavior, configuration or structure changed.
- **Do not commit, stash, revert or push unless the user asks.** Leave the changes in the working tree for the owner to review. Never rewrite history.
